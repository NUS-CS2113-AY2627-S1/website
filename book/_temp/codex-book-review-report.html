Independent content and curriculum review

Make the book more internship-ready by trading taxonomy for workflow.

The book has a strong foundation in requirements, design, code quality, and systematic testing. Comparison with a model syllabus synthesized from ten recent peer courses confirms those strengths. Its biggest opportunity is to reallocate time from prerequisite repetition, detailed UML, test taxonomy, and historical process material toward collaborative workflow, quality feedback, responsible delivery, and AI-assisted engineering.

25 core chapters reviewed 18 generic-syllabus topics benchmarked 10 recent peer courses inform the baseline Live AY2026/27 deployment checked Audience: Java + basic OOP assumed

Executive verdict

The book broadly matches the conceptual center of a representative introductory software engineering course, but the match is uneven. It gives strong chapter-level treatment to 9 of the model syllabus's 18 topic rows, partial treatment to 8, and no evident treatment to AI-assisted software engineering. Do not expand it by simply adding more chapters: reclaim space from low-return detail and deepen the partial topics.

1

Correct the misleading parts first

Several examples and absolute claims can teach the wrong mental model. These include Java composition, thread-unsafe Singleton code, “proper” isolated unit tests, a non-compiling coverage example, and a 2011 description of Scrum.

2

Shift from definitions to doing

Some thin chapters name techniques without teaching students how to perform them. Requirements gathering, IDE/debugging, QA, project planning, and teamwork need worked workflows, failure modes, and practice tasks.

3

Rebalance toward internship work

The core path underweights the issue → branch → code → test → PR → review → CI → release loop. This is also the clearest gap against the generic syllabus: Git is supplementary, CI is mostly definitional, and review/team practices are too brief.

4

Add a security baseline

Security is currently a list item, not a capability. Students need input validation, authorization, secrets, dependency risk, safe logging, and secure review at beginner depth.

5

Modernize examples and terminology

Replace dated product/tool references that distort the concept. Java EE, Windows-only .NET, XML-centric SOA, FindBugs, old GitHub Project Boards, Firefox OS, and legacy CI tool lists are clear targets.

6

Keep the book’s distinctive strengths

Preserve the beginner-friendly explanations, explicit learning outcomes, bold skim layer, and project-linked examples. Code quality, requirements specification, EP/BVA, and design trade-offs remain valuable after tightening; the peer benchmark confirms that these belong in the core.

Recommended top-level decision: aim for a roughly 20–30% reduction in the examinable reading devoted to prerequisite OOP, advanced UML notation, repeated testing taxonomy, and historical process descriptions. Reinvest that space in five practical strands: collaborative workflow, secure development, diagnosis and automated quality feedback, teamwork and delivery, and responsible AI-assisted engineering.

The book covers the representative core more convincingly than a gap-only review might suggest. The comparison below uses the 18 topic rows in the model syllabus synthesized from Brown, MIT, UNSW, Edinburgh, Illinois, Texas, Washington, Imperial, Berkeley, and Georgia Tech. “Strong” means the book gives the topic direct, substantial treatment; it does not mean every example is current or every skill is practiced.

9

Strongly represented

Half of the generic topic rows have clear chapter-level coverage. Requirements, design, modeling, patterns, maintainability, processes, and testing form a solid conventional SE core.

8

Present but incomplete

The main issue is depth of practice, not total absence. Teamwork, collaborative workflow, correctness, debugging, advanced testing, delivery, professional responsibility, and communication need stronger applied treatment.

The peer comparison changes the emphasis of the recommendations, not their overall direction. Requirements, architecture, modeling, object-oriented design, patterns, maintainability, testing, and process coverage should be tightened and refreshed—not displaced. The highest-return additions are the missing connective tissue: collaborative workflow, applied quality feedback, responsible delivery, professional considerations, and AI use.

Optional implementation contexts are not core gaps

The generic syllabus deliberately separates transferable SE topics from platform choices. Web UIs, HTTP services, databases, cloud/container deployment, concurrency, and grammars appear unevenly across the ten peer courses. CS2103/T can continue using a Java desktop codebase as its main context, provided students encounter realistic interfaces, dependencies, failures, integration, and release constraints. HTTP/API, data, cloud, and concurrency material should be selected extensions, not a reason to turn the course into full-stack training.

Where to reduce and where to increase

The current source-volume distribution is a useful warning signal, even though word count is not the same as teaching time. Large bodies of modeling and testing material coexist with very small chapters on requirements, debugging, QA, and teamwork. The generic-syllabus comparison indicates that the solution is better balance and stronger application, not deletion of the well-covered design and testing core.

Reduce or consolidate

  • OOP prerequisite repetition: make it a diagnostic refresher, not a second introductory course.
  • Advanced UML mechanics: keep the diagrams students must read and produce; demote notation edge cases.
  • Testing taxonomies: compress alpha/beta, dogfooding, and similar labels into a comparison map.
  • Long test-input walkthroughs: retain EP, BVA, decision tables, and pairwise coverage with fewer repeated examples.
  • Historical process descriptions: shorten waterfall/XP/Scrum history and teach modern flow and feedback.
  • C++ to Java: remove from the core index for a cohort already assumed to know Java.

Increase or add

  • Collaborative delivery: issues, task slicing, branches, small commits, PRs, review, CI gates, releases.
  • Secure engineering: validation, access control, secrets, dependency/supply-chain risk, safe logs.
  • Debugging and diagnosis: reproduction, stack traces, breakpoints, call stacks, logs, and minimal test cases.
  • Team effectiveness: communication, ownership, conflict, review etiquette, decisions, onboarding, async work.
  • Responsible AI-assisted engineering: bounded use, privacy, disclosure, diff inspection, API verification, and evidence.
  • One modern implementation context: connect Gradle dependencies, an HTTP/JSON interface, configuration, failure handling, logs, and release evidence without attempting a full-stack survey.

Concept wrinkles and correctness issues

These are the highest-value editorial fixes because a beginner is unlikely to recognize the caveat independently. They should be fixed before broader restructuring.

PriorityLocationCurrent wrinkleRecommended correction
P0 OOP → Composition “Composition is implemented using a normal variable” and the part will be deleted with the whole. A Java field does not enforce exclusive ownership or deterministic deletion. Explain composition as a modeling/lifecycle constraint that the design and API must preserve; other references can still keep the object reachable.
P0 Design Patterns → Singleton The lazy getInstance() implementation is not thread-safe, but appears as the typical implementation. Either use an enum/eager Java example or explicitly scope the sample to single-threaded code. Lead with global-state, lifecycle, and testability costs before implementation.
P0 Testing → Coverage The example declares void findRate(int input) but returns 0, -1, and cap. Change the return type to int. Add an automated compile check for every Java snippet that is intended to compile.
P0 Testing → Unit tests A “proper” unit test is said to require full isolation, and one or more tests per public method is presented as common practice. Teach isolated and sociable unit tests as legitimate choices. Test observable behavior and risks rather than mechanically mirroring every public method.
P0 Testing → TDD TDD is said to “guarantee” that code is testable. Replace “guarantees” with “strongly encourages.” Poorly factored or over-mocked tests can still accompany hard-to-test code.
P0 Testing → GUI automation All product-level testing of a GUI product is said to need to go through the GUI. Clarify that product-level behavior can be tested through APIs, service boundaries, and other interfaces. Reserve end-to-end UI tests for critical journeys and UI-specific behavior.
P0 Process Models → Scrum The chapter says it is adapted from Wikipedia retrieved in 2011; it uses obsolete role language, co-location assumptions, commitment wording, and the old three-question Daily Scrum format. Rewrite from the current official Scrum Guide or teach Scrum as one example rather than a normative process. Emphasize the Sprint Goal, accountabilities, inspection, and adaptation.
P0 Reuse → Platforms Java EE is treated as current, and .NET is described as usually running on Windows. Use Jakarta EE terminology and describe modern .NET as cross-platform. Better still, teach what a platform provides through current examples without relying on a fixed product list.
P1 Requirements → NFRs NFRs are defined only as constraints, while the examples mix quality attributes, project constraints, scope exclusions, process requirements, and business rules. Separate quality attributes from constraints and business rules. Express important qualities as measurable scenarios, e.g., response time under a stated workload.
P1 Error Handling → Exceptions Exceptions are restricted to “unusual” conditions. Frame the choice around API contracts and recovery boundaries. Cover invalid input, environmental failure, domain failure, preserving causes, translation, and cleanup.
P1 Error Handling → Assertions Students are told to use assertions liberally, without foregrounding that Java assertions are disabled by default. State the runtime fact first. Use assertions for internal invariants during development; use exceptions or validation for public/API preconditions and required production behavior.
P1 Integration → CI/CD CI jumps directly to continuous deployment; continuous delivery is not distinguished. Teach CI, continuous delivery, and continuous deployment as separate capabilities. Include artifact creation, environment promotion, approval/rollback, and why deployment frequency depends on context.
P1 Architecture Architecture is described as typically designed by “the software architect,” while architecture diagrams are presented as almost entirely free-form. Present architecture as a team-owned set of consequential decisions. Teach audience, scope, viewpoint, legend, boundaries, dependency direction, and explicit trade-offs.
P1 Test Case Design “Random” testing is described as generating with another strategy and randomly selecting a subset. Distinguish random sampling, fuzzing, and property-based generation. Require reproducible seeds and meaningful test oracles.
P2 Code Quality Hard numbers such as “consider shortening beyond 30 LoC” can be remembered as rules rather than signals. Teach thresholds as prompts for judgment. Cohesion, naming, control flow, duplication, and change frequency matter more than a universal line count.
Add executable-documentation checks. Extract compilable Java snippets into a small Gradle test fixture, compile them in CI, and use link checking for external references. This would have caught the void-return example and will prevent future Java/API drift.

Missing or under-covered internship basics

The best additions are cross-cutting strands tied to the team project, not isolated theory chapters. Each strand should end in a visible project artifact or workflow. Against the generic syllabus, collaborative workflow, debugging/quality feedback, teamwork, professional responsibility, delivery, and AI are core-alignment priorities. Dependencies, HTTP, data, operations, and concurrency are implementation-context options whose depth should depend on the project.

PriorityCapability to addBeginner-level outcomesBest home
P0 Collaborative Git/PR/CI workflow Take a small issue from definition to merge. Slice work, branch, make reviewable commits, open a PR, respond to review, interpret CI, and merge safely. Elevate the Git trail; connect Integration, QA, Teamwork, and Project Planning.
P0 Secure software development Recognize and prevent common beginner risks. Validate untrusted input, distinguish authentication/authorization, avoid committed secrets, review dependencies, handle sensitive logs, and apply least privilege. New short core strand threaded through Requirements, Design, Reuse, QA, and Error Handling.
P0 Debugging and diagnosis Move from a symptom to a defensible cause. Reproduce, minimize, read a stack trace, use breakpoints/watch/call stack, form hypotheses, add a regression test, and verify the fix. Expand IDEs; reinforce in Testing and Error Handling.
P0 Team collaboration Work effectively in a brownfield team. Communicate status and risk, ask for help, give respectful review feedback, record decisions, resolve disagreements, share ownership, and onboard to unfamiliar code. Rewrite Teamwork; practice in PRs and project retrospectives.
P1 Dependencies and supply chain Add a dependency deliberately. Inspect direct/transitive changes, license and maintenance signals, pin/lock versions appropriately, react to a vulnerability alert, and update safely. Reuse + Integration + QA.
P1 HTTP/API and failure basics Read and use a small web API. Understand request/response, JSON, status codes, idempotency, versioning, validation, authentication tokens, timeout, retry, and rate-limit behavior. Architecture + Reuse/APIs + Error Handling.
P1 Data and persistence basics Make safe changes to persistent data. Understand schema, constraints, transactions, serialization, migration/backward compatibility, backup, and test isolation. Architecture + Integration + Testing.
P1 Operational visibility Produce diagnostic evidence without leaking data. Use useful log levels, structured context, correlation identifiers, health signals, and a minimal incident timeline; know when to roll back. Error Handling/Logging + Integration.
P1 Accessibility, privacy, and ethics Treat quality attributes as design inputs. Identify affected users, collect only needed data, obtain consent where appropriate, make basic accessible choices, and surface ethical trade-offs. Requirements + Design + QA.
P2 Concurrency and asynchronous failures Recognize shared-state and timing risks. Explain races, atomicity, thread safety, ordering, cancellation, and why retries can duplicate effects. Design Patterns + Architecture + Error Handling + Testing.
P0 AI-assisted engineering literacy Use an AI tool without outsourcing judgment. Provide bounded context, inspect diffs, verify APIs, run tests/static checks, protect private data, and disclose/attribute use as required. Short course-wide practice note; assess the resulting engineering evidence, not prompt trivia.

Chapter-by-chapter recommendations

Every core chapter can remain represented, but several should become shorter sections inside a more coherent workflow. “Reduce” means compress or demote—not delete the concept entirely.

Software Engineering Rewrite Replace the long Brooks “joys and woes” extract as the main introduction. Keep a short historical sidebar, then introduce SE as managing change, collaboration, uncertainty, quality, and trade-offs across a socio-technical lifecycle. The current chapter is evocative but does not orient students to the course.
Object-Oriented Programming Reduce Turn this into a diagnostic refresher because Java and basic OOP are prerequisites. Retain abstraction, encapsulation, polymorphism, interfaces, substitutability, and composition; demote class basics, enumerations, overloading, aggregation, association classes, and binding terminology. Correct the composition ownership model and avoid duplicating UML association notation.
Requirements Increase Expand the unfinished foundation—the source still contains “TODO: add more details.” Separate goals, functional behavior, quality attributes, constraints, assumptions, and business rules. Teach measurable quality scenarios, stakeholder conflicts, scope, prioritization by value/risk, traceability, and change management.
Gathering Requirements Increase Convert seven one-paragraph definitions into a usable discovery workflow. Teach interview and survey question design, sampling and bias, observation ethics/consent, prototype fidelity, competitive analysis, triangulation, synthesis, and validation. Require students to produce evidence and decisions, not merely name elicitation techniques.

Add acceptance criteria, examples/Given–When–Then, quality constraints, assumptions, and traceability to tests. Shorten the extended use-case mechanics and the long brainstorming recipe where project instructions already repeat it. Replace the obsolete GitHub Project Boards link.

Design Fundamentals Keep + increase Preserve abstraction, coupling, and cohesion as durable ideas. Add information hiding, stable interfaces, dependency direction, data/control/deployment coupling, and examples of when duplication can be cheaper than premature abstraction. Make trade-offs explicit rather than implying “lower coupling and higher cohesion” are context-free maxima.
Modeling (Using UML) Reduce Shift the goal from notation mastery to communicating a decision accurately. Prioritize class/object/sequence/activity basics and diagram-code consistency. Demote advanced class/sequence notation, use-case diagrams, and customization details; add context/container/component views, deployment boundaries, and diagrams-as-code. Teach students to choose the smallest diagram that answers an audience’s question.
Software Architecture Modernize Replace the old style catalog with modern trade-off reasoning. Keep layered, client–server, and event-driven foundations; update XML-centric SOA to services using HTTP APIs and/or messaging; compare modular monolith and distributed services at beginner depth. Replace Firefox OS and generic SOA graphics, and add data ownership, failure boundaries, deployment, and architecture decision records.
Software Design Patterns Rebalance Teach patterns as contextual trade-offs, not a catalog to recognize. Demote Singleton and present it first as constrained global state; if retained, fix thread safety. Keep Command/Observer/Facade where they match the project, and consider Strategy/Adapter plus dependency injection as more transferable internship patterns. Require “problem, forces, consequences, alternatives.”
Design Approaches Merge Merge the useful ideas into Design Fundamentals and Architecture. Retain top-down/bottom-up movement and evolutionary design, but remove the false binary of emergent design versus up-front design. Add spikes/prototypes, decision records, and “just enough design now, revisit with evidence.”
IDEs Increase Make this a practical codebase-navigation and debugging chapter. Add symbol search, usages, call hierarchy, debugger breakpoints, conditions, watches, call stacks, exception breakpoints, test navigation, and Git diff tools. Teach a diagnosis loop—reproduce, narrow, hypothesize, inspect, prove, regress—rather than only ranking print statements, eyeballing, and debugger use.
Code Quality Keep + tune This is one of the book’s strongest internship-facing chapters. Preserve naming, readability, scope, duplication, happy paths, and useful comments. Recast hard thresholds and slogans (30-line methods, three nesting levels, “SLAP hard”) as diagnostic prompts; add immutability, null handling, API consistency, automated formatting/linting, and careful handling of warnings.
Refactoring Increase Expand from catalogs to a safe brownfield workflow. Add characterization tests, small behavior-preserving steps, IDE-assisted refactors, frequent test runs, reviewable commits, and when not to refactor. Avoid implying “make it work now, improve it later” is always safe; show continuous cleanup around the code being changed.
Documentation Increase Retain the strong top-down guidance and four documentation purposes, but broaden the artifacts. Add README, setup/run/test instructions, CONTRIBUTING, API examples, architecture decisions, diagrams, troubleshooting, and ownership/maintenance. Replace the applet-era Javadoc example and teach when generated reference is insufficient.
Error Handling Modernize Teach failures across boundaries, not only exceptions/assertions. Cover validation, domain versus infrastructure failures, exception translation and preserved causes, try-with-resources, cleanup, user-facing messages, timeouts/retries/idempotency, and safe structured logging. Qualify assertion advice because Java assertions are disabled by default.
Integration Rewrite Center the chapter on the modern integration loop. Keep early/frequent and incremental integration, then teach reproducible Gradle builds, pull requests, automated checks, branch protection, artifacts, configuration, releases, rollback, and the difference between continuous delivery and deployment. Retire the generic Travis/AppVeyor/Jenkins tool list in favor of one maintained GitHub Actions walkthrough.
Reuse Modernize The cost/benefit section already identifies licenses, vulnerabilities, malicious dependencies, and abandonment—promote those from warnings to skills. Teach Gradle manifests, direct/transitive dependencies, versions/locks, update policy, dependency review, and SBOM awareness. Update GitHub API, Java EE/Jakarta EE, and .NET examples; add small HTTP/JSON API use and failure handling.
Quality Assurance Rebalance Make risk-based quality strategy the chapter’s organizing idea. Expand PR review and static analysis into practical workflows; include formatters, nullness/type checks, SAST, dependency review, and secret scanning. Demote formal verification to a short “specialized techniques” sidebar. Replace FindBugs with SpotBugs or a current project tool.
Testing Keep + reduce Keep unit/integration/system/regression testing, automation, testability, coverage, DI, and TDD, but compress the taxonomy. Teach behavior-focused tests, isolated versus sociable units, test-double roles, parameterized tests, deterministic tests, flaky-test diagnosis, test selection in CI, and the limits of coverage. Fix the non-compiling coverage snippet and qualify TDD claims.
Test Case Design Reduce + extend Retain equivalence partitioning, boundary values, decision logic, and pairwise combinations. Condense repeated “valid once/invalid separately” walkthroughs into a checklist and one integrated example. Correct random-testing terminology; add property-based and metamorphic testing as optional modern extensions, with reproducible seeds and explicit oracles.
SDLC Process Models Modernize Reduce model history and teach how teams manage flow and feedback. Update Scrum from the official guide, retain selected XP practices, add Kanban/WIP/lead-time concepts, and emphasize that real teams adapt practices to risk and context. Avoid equating agile with little design or documentation.
Project Planning Rebalance Prioritize issue quality, work slicing, dependencies, milestones, uncertainty, and risk over Gantt mechanics. Teach a current GitHub Projects workflow, blockers, acceptance criteria, estimates as uncertain forecasts, explicit buffers, and lightweight status/risk communication. Keep Gantt as recognition-level.
Teamwork Rewrite Replace the outdated egoless/chief-programmer/strict-hierarchy taxonomy. The current 407-word chapter does not prepare interns for collaborative engineering. Teach team norms, shared ownership with clear responsibilities, communication, conflict resolution, psychological safety, inclusive language, code-review etiquette, decision records, handoffs, onboarding, and remote/async work.
Principles Keep + tune Teach principles as competing heuristics, not acronym recall. Keep separation of concerns, SRP, LSP, and Law of Demeter with counterexamples; add composition over inheritance, information hiding, and least privilege. Reduce the duplicated SOLID wrapper and make DIP/ISP concrete if they remain examinable.

Supplementary material

The supplementary routes contain some of the most internship-relevant practice, but the current labeling makes their importance unclear.

C++ to Java

Remove it from the main textbook chapter list for this cohort. Students are assumed to know Java, while this source is roughly 20k words and includes dated Java-edition and installation explanations. Keep a separate “Java readiness check” with links to targeted refreshers: collections, exceptions, generics, streams, JUnit, Gradle, and the course’s supported JDK.

Specific cleanup: replace Java EE with Jakarta EE; stop presenting the JRE as the normal separate install; replace Java 8 “new features” framing; remove Java ME as a central platform category; and keep current JUnit 5 material as a testing quickstart.

Git Learning Trail

Promote the essential workflow into the course’s core skill path. Keep staging, commits, branches, remotes, merge conflicts, PRs, and reviews. Reduce low-frequency operations and GUI-specific screenshots; prefer git switch/git restore for beginner intent, use main in new examples, and explain that repository branch names vary.

Add small PRs, review responses, protected branches/rulesets, required CI checks, secret avoidance, and safe history rewriting. The trail currently contains extensive master, checkout, and Sourcetree-specific material that creates avoidable maintenance cost.

Project Duke

Keep the project as the bridge from reading to doing. Map each increment explicitly to the revised skills: issue, acceptance criteria, branch, focused commit, tests, refactor, PR/review, CI evidence, release note, and short retrospective. A CLI remains a sensible beginner scope if the book acknowledges that real internship systems may expose web, service, data, and asynchronous boundaries.

Definitions and combined exercises

Use definitions as reference, not as a shadow syllabus. Remove stale entries for topics that are no longer taught and add terms introduced by the revised workflow. Update exercises so more questions ask students to choose, diagnose, review, or justify—not only recognize a label.

A more coherent curriculum shape

Organize the book around the lifecycle of a change in an existing codebase. This preserves the existing knowledge while giving beginners a mental map that matches internship work.

A

Orient and enter the codebase

SE overview; Java/OOP diagnostic; Git essentials; IDE navigation; build and run; debugging a known defect.

B

Understand the change

Stakeholders; discovery evidence; requirements; quality/security constraints; acceptance criteria; issue definition.

C

Design the change

Abstraction, coupling, cohesion; small models; architecture boundaries; APIs/data; patterns and principles as trade-offs.

D

Implement safely

Code quality; error handling; dependencies; secure coding; responsible AI use; refactoring; developer documentation; focused commits.

E

Establish confidence

Test design; unit/integration/system tests; static/security analysis; review; coverage limitations; regression evidence.

F

Integrate and learn

PR/CI gates; artifacts and release; configuration; logs/health; rollback; teamwork; retrospective and next issue.

Use one running brownfield scenario across the six stages. The same feature should begin as an ambiguous stakeholder request, become an issue with acceptance criteria, require a design decision, introduce a dependency or failure mode, receive tests and review, and pass CI. Reusing one change reduces cognitive load and shows how the chapters connect.

Practical implementation roadmap

Separate correctness work from curriculum restructuring so improvements can ship safely and incrementally.

Phase 1 — Correct and refresh

Immediate Fix the composition, Singleton, coverage, unit-testing, TDD, GUI-testing, assertion, Scrum, Java EE/.NET, CI/CD, GitHub API/Projects, and FindBugs issues. Replace broken/HTTP links and gendered historical prose where it appears as current narration. Add snippet compilation and link checks.

Phase 2 — Reclaim space

Next Shorten OOP, advanced UML, repeated testing taxonomy, extended test-input examples, historical process descriptions, Gantt detail, and C++-to-Java placement. Merge Software Design and Design Approaches into stronger neighboring chapters.

Phase 3 — Deepen the missing and partial strands

Next Write focused beginner modules for collaborative PR/CI workflow, secure development, debugging/diagnosis, teamwork/delivery, and responsible AI-assisted engineering. Add one selected dependency/API/failure context to the project rather than a broad platform survey. Each module should produce a project artifact and include a “common failure” exercise.

Phase 4 — Align assessment and project work

Then Replace recognition-heavy questions with small decisions and reviews: critique an issue, diagnose a stack trace, review a diff, choose a test boundary, evaluate a dependency, or justify an architecture trade-off. Require verification and disclosure evidence for permitted AI use. Ensure project rubrics reward the same behaviors.

Phase 5 — Establish a maintenance cadence

Ongoing Before each academic year, run compile/link checks, review tool screenshots, verify official process references, sample internship feedback, and retire examples whose product or API has become obsolete. Mark time-sensitive pages with an explicit “last verified” field.

Method, scope, and sources

The review combined the deployed book’s actual chapter map with the local MarkBind sources and a generic syllabus synthesized from ten recent peer courses. It focused on conceptual accuracy, relevance, balance, omissions, modernization for internship readiness, and coverage of a representative introductory software engineering core.

What was inspected

  • The live AY2026/27 textbook index and its combined printable outline, generated 23 July 2026.
  • All 25 core chapter families in the local book source, including their topic hierarchy and course-specific inclusion priorities.
  • The 18-topic model in codex-generic-syllabus.md, synthesized from the ten recent university courses recorded in peer-courses.md.
  • For each model-syllabus topic, explicit chapter or subtopic evidence in the published index and local source. A “partial” rating means that important elements are thin, definitional, supplementary, or disconnected from a practiced workflow; “not evident” means no matching topic was found in the inspected book material.
  • Supplementary C++-to-Java, Git Learning Trail, Project Duke placement, definitions, and exercise structure at a lower level of detail.
  • Source markers indicating unfinished or stale content, including explicit TODOs, old retrieval dates, legacy product names, and obsolete documentation URLs.

Current primary references used to validate modernization findings

  • The Scrum Guide (current official version) — current accountabilities, events, goals, and terminology.
  • GitHub Docs: Planning and tracking with Projects — current Projects capabilities and issue/PR integration.
  • GitHub Docs: Protected branches — required reviews and status checks.
  • GitHub Docs: Building and testing Java with Gradle — a current beginner CI workflow.
  • GitHub Docs: Supply-chain security and secret scanning — dependency and credential risks that interns can encounter directly.
  • NIST SP 800-218 Secure Software Development Framework — security practices integrated across the SDLC.
  • OWASP Top 10:2025 — current awareness areas, including access control, supply-chain failure, insecure design, logging, and exceptional conditions.
  • DORA: Continuous delivery — the distinction between continuous delivery and continuous deployment.
  • Jakarta EE FAQ and official .NET platform information — current platform names and cross-platform status.
  • Oracle Java launcher documentation — Java assertions are disabled by default.

Limitations

The textbook is being used as a proxy for course topic coverage, not as proof of everything students experience. The comparison does not fully audit weekly briefings, tutorials, project instructions, assessment rubrics, or instructor feedback, so a “partial” or “not evident” book rating may be taught elsewhere in the course. This is also a content audit rather than a learning-effectiveness study: it does not use student outcome data, internship supervisor interviews, quiz-item statistics, or classroom observation. Before a major rewrite, validate the priority list against the full course and with recent interns, tutors, and employers.

Bottom line: the generic-syllabus benchmark validates the book’s requirements, design, maintainability, process, and testing core. The next version should tighten that material and add a stronger through-line from ambiguous request to reviewed, tested, secure, responsibly AI-assisted, integrated, and communicated change in a shared codebase.
